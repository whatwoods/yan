# 砚 v1.0 — Implementation Design

_Supplement to the product vision spec (`docs/specs/2026-05-03-砚-vision.md`)._

This document defines the concrete architecture, module boundaries, and data flow for building v1.0 from the current prototype.

---

## 1. Strategy

**Approach:** Incremental layer-by-layer. Migrate to Vite first, then add M1 → M2 → M3 features. The existing UI stays working at every step.

**Build order:**

1. Vite migration — scaffold, npm install, port existing code, verify identical behavior
2. M1: Data infrastructure — IndexedDB, Markdown format, categories, migration, soft-delete, encryption, WebDAV sync
3. M2: AI — BYOK providers, auto-classify/tag/summarize, monthly insights, Tag Curator, RAG Tier 1
4. M3: Polish — offline queue, performance, error recovery, PWA install, mobile tuning

## 3. Data Layer

### 3.1 IndexedDB Schema (via `idb` package)

**Database name:** `biji-v1`

**Object stores:**

| Store | Key | Indexes | Purpose |
|---|---|---|---|
| `notes` | `id` (string) | `category`, `created`, `modified`, `pinned`, `deleted_at` | All notes |
| `meta` | key (string) | — | Settings, categories, sync state, encrypted secrets |
| `sync_queue` | auto-increment | `note_id`, `created` | Pending writes for offline queue |

### 3.2 Note Data Model

```js
{
  id: "2026-05-03-1742-a3f",      // YYYY-MM-DD-HHMM-<3char fingerprint>
  created: "2026-05-03T17:42:13+08:00",
  modified: "2026-05-03T17:43:01+08:00",
  kind: "text",                    // text | voice | photo | mixed
  category: "工作",                // exactly one from categories list
  tags: ["产品", "首屏", "决策"],   // zero to N
  people: ["阿宁"],                // AI-extracted
  pinned: false,
  title: "晚饭后又重新想了一遍首屏",
  body: "Markdown正文...",
  summary: "建议把输入框作为视觉中心…",
  ai: {
    summary: "建议把输入框作为视觉中心…",
    generated_at: "2026-05-03T17:42:18+08:00",
    model: "deepseek-chat"
  },
  attachments: ["photo-1.jpg"],
  deleted_at: null                 // ISO string when soft-deleted
}
```

### 3.3 ID Generation

Format: `YYYY-MM-DD-HHMM-<3char>`. The 3-char suffix is a random alphanumeric string generated once on first launch and stored in IndexedDB `meta` as `device_fingerprint`. Same fingerprint is used as the PBKDF2 salt for master password derivation. Time-sortable, device-distinguishable, conflict-resistant.

### 3.4 Markdown Serialization (`note-format.js`)

- `serialize(note)` → Markdown string with YAML frontmatter (using `gray-matter.stringify`)
- `deserialize(markdownString)` → note object (using `gray-matter`)
- Body is raw Markdown below the frontmatter block
- Attachments are NOT embedded — stored separately on WebDAV

### 3.5 Category System

7 defaults (spec §10.2), stored in IndexedDB `meta` store as `categories`:

```js
[
  { name: "学习", color: "竹青", hex: "#5b7a5a" },
  { name: "工作", color: "群青", hex: "#3d5a7c" },
  { name: "生活", color: "藤黄", hex: "#c89342" },
  { name: "想法", color: "梅紫", hex: "#8b4a5e" },
  { name: "AI", color: "印章红", hex: "#b8443a" },
  { name: "开发", color: "茶色", hex: "#8b6f47" },
  { name: "收藏", color: "墨色", hex: "#1f1a14" }
]
```

Users can add/edit/delete categories. Synced as `categories.json` on WebDAV.

### 3.6 Migration from localStorage

On first launch after upgrade:
1. Read `biji.notes.v1` from localStorage
2. Convert each old note: generate new ID, assign category based on existing tag-to-category mapping, preserve timestamps
3. Write to IndexedDB
4. Clear localStorage copies
5. Set `meta.migrated = true`

## 4. WebDAV Sync (`sync.js`)

### 4.1 Dependencies

`webdav` npm package for WebDAV client operations.

### 4.2 Directory Layout

```
/biji/
├── notes/2026/05/03-1742-a3f.md
├── attachments/2026-05-03-1742-a3f/photo-1.jpg
├── trash/2026-04-15-...md
├── conflicts/<id>.<device>.md
├── categories.json
├── insights/2026-05.md
├── secrets.enc
├── preferences.md
└── curator-rejected.md
```

### 4.3 Sync Flow

**Push (local → remote):**
1. Serialize note to Markdown via `note-format.serialize()`
2. PUT to `notes/YYYY/MM/<id>.md`
3. Upload attachments if any
4. On failure: add to `sync_queue` for retry

**Pull (remote → local):**
1. PROPFIND `notes/` for last 6 months
2. Compare remote `modified` with local `modified`
3. GET changed files, deserialize, upsert into IndexedDB
4. Detect conflicts (see below)

### 4.4 Sync Triggers

- App startup (after IndexedDB loaded)
- Network recovery (`online` event)
- 5s debounce after any local write
- Manual pull-to-refresh gesture

### 4.5 Conflict Resolution

If a note has been modified both locally and remotely since last sync:
- Keep local version as-is
- Save remote version to `conflicts/<id>.<device>.md`
- Show banner in "本" screen: "有 N 条冲突待处理"
- Conflict view shows side-by-side diff, user picks one

### 4.6 Offline Queue

Failed writes go to IndexedDB `sync_queue` store. On next sync trigger, drain queue FIFO. 3 consecutive failures → show "未同步" indicator, auto-retry on network recovery.

## 5. Encryption (`crypto.js`)

### 5.1 Master Password Flow

```
First setup:
  user sets password (≥8 chars)
  → PBKDF2(password, device_fingerprint, 600,000 rounds) → AES-GCM key K
  → encrypt(JSON.stringify({apiKeys, modelAssignments})) with K
  → store blob as secrets.enc on WebDAV

New device:
  pull secrets.enc
  → prompt user for password
  → derive K same way
  → decrypt → keys in memory for session
```

### 5.2 Scope

- Encrypts: API keys, model assignments
- Does NOT encrypt: notes, categories, preferences (v1 assumption: WebDAV is trusted)
- Password never stored — only held in memory during active session
- Lost password = keys lost, must re-enter

## 6. AI Integration (`ai.js`)

### 6.1 Protocol

All calls use native `fetch` to OpenAI-compatible endpoints:
- `GET /v1/models` — list available models
- `POST /v1/chat/completions` — generate completions

### 6.2 Preset Providers (spec §8.2)

| Name | Endpoint |
|---|---|
| 魔搭 ModelScope | `https://api-inference.modelscope.cn/v1` |
| DeepSeek | `https://api.deepseek.com/v1` |
| Moonshot Kimi | `https://api.moonshot.cn/v1` |
| 智谱 GLM | `https://open.bigmodel.cn/api/paas/v4` |
| 通义千问 | `https://dashscope.aliyuncs.com/compatible-mode/v1` |
| MiniMax | `https://api.minimax.chat/v1` |
| 小米 | `https://token-plan-cn.xiaomimimo.com/v1` |
| OpenRouter | `https://openrouter.ai/api/v1` |
| OpenAI | `https://api.openai.com/v1` |
| 自定义 | user-provided base URL |

### 6.3 Task-Level Model Assignment

Stored in `secrets.enc` alongside API keys:

```js
{
  classify: "qwen-turbo",     // cheap, every note
  tag: "qwen-turbo",          // cheap, every note
  summarize: "qwen-turbo",    // cheap, every note
  insight: "deepseek-v3",     // mid-tier, monthly
  ask: "deepseek-r1",         // strong, on-demand
  curator: "deepseek-r1"      // strong, weekly
}
```

### 6.4 Auto-Classification Pipeline (on save, 1.5s debounce)

Two parallel calls:

1. **Classify** (closed set): "从以下分类中选一个：{categories列表}. 笔记：{body前200字}" → returns single category name
2. **Extract** (open set): "提取标签和人名. 笔记：{body前200字}" → returns `{tags: [], people: []}`

On failure: fall back to existing rule-based keyword dictionary (silent, no error shown).

### 6.5 Monthly Insights

- Trigger: 1st of month, idle, or manual
- Gather all notes from past month → build context (titles, summaries, tags, categories)
- Call insight model with structured prompt → generate summary
- Store result as `/biji/insights/YYYY-MM.md`
- Display in "砚" screen

### 6.6 Tag Curator (`curator.js`)

- Trigger: weekly (Sunday morning) or every 50 new notes
- Gather tag statistics (frequency, co-occurrence, last-used date)
- Call curator model → returns structured suggestions:
  ```js
  [{ type: "merge", from: ["产品", "产品设计"], to: "产品", reason: "..." },
   { type: "rename", from: "感受", to: "情绪", reason: "..." },
   ...]
  ```
- Suggestions stored in IndexedDB `meta` store
- Shown in "砚" screen: "砚整理了 N 条建议"
- User can accept (batch-update frontmatter) or reject (add to `curator-rejected.md`)
- Accepted merges feed back into future auto-tagging (tag name preference)

### 6.7 RAG Tier 1 (`rag.js`)

Two-step pipeline:

1. **Query parsing** (cheap model, ~100 tokens):
   ```
   用户问："{question}"
   返回 JSON: {time_range, categories, tags, people, free_text}
   ```
   On failure → fallback to "last 50 notes by time"

2. **Candidate retrieval**: Filter in-memory index by parsed structured fields → ~30 candidates

3. **Answer generation** (strong model, ~3-5k tokens):
   ```
   候选笔记：[{title, summary, tags}, ...]
   用户问："{question}"
   回答并引用相关笔记.
   ```

## 9. Media Handling

### 9.1 Photo Compression

Per spec §13.5: before storing a photo, compress client-side to long edge 1920px, JPEG quality 85. Single photo max 5MB — if超出, show prompt to crop. Use Canvas API for compression (no additional dependency). Compressed photo stored in IndexedDB as blob; synced to WebDAV `attachments/<id>/` directory.

### 9.2 Voice Notes

Use browser Web Speech API (`zh-CN`) for real-time transcription (existing behavior). On iOS Safari where Web Speech API is unavailable: record to file → upload to OpenAI-compatible Whisper endpoint for transcription. If provider doesn't support Whisper, disable voice button on iOS with tooltip.
